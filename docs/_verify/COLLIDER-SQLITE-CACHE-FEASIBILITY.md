# Feasibility: precompute full-world LOD0 collider → SQLite cache (coop host FPS)

Дата: 2026-07-25. Метод: WebSearch/WebFetch официальной доки
`voxel-tools.readthedocs.io` + GitHub issues `Zylann/godot_voxel`, чтение
`bootstrap.gd`/`coop_session.gd`/`remote_player.gd`. Только research — код
не менялся, коммитов нет.

Базируется на `docs/_verify/VOXEL-TOOLS-COOP-DIG.md` (не повторяю то
research, только ссылаюсь).

## Вердикт (RU)

**НЕ РАБОТАЕТ.** SQLite в Voxel Tools хранит только voxel-данные (SDF/материал
блока), не коллайдер; коллайдер (`ConcavePolygonShape3D` + регистрация тела в
`PhysicsServer3D`) в API плагина **всегда** строится заново из меша на главном
потоке каждого процесса (и host, и guest — это два разных запущенных Godot,
не общая физика) — кэш в SQLite физически не может подсунуть готовый
коллайдер мимо этого пути, а «весь мир от L0» для шара Ø19 км — это
~4–9 млн блоков, десятки ГБ и часы генерации на старте, что само по себе
нежизнеспособно отдельно от вопроса про коллайдер.

Однокоренная здравая часть идеи — «перестраивать только изменённую часть
меша/коллайдера» — **это уже то, как Voxel Tools работает нативно**
(блочная архитектура + `collision_update_delay` коалесит правки), добавлять
нечего.

## 1. Декомпозиция стоимости: что SQLite-кэш вообще может убрать

| Стадия | Где выполняется | Дорого? | SQLite-кэш SDF отменяет? |
|---|---|---|---|
| Генерация SDF (генератор планеты) | Poток (или main для root, `cache_generated_blocks`) | Да для Ø19 км аналитик-генератора (см. `_configure_dig_stream` коммент: «Ø19 km analytic gen is heavy») | **Да, частично** — это именно то, что `save_generator_output = true` в `_configure_dig_stream` УЖЕ делает: сгенерированная кора сохраняется в тот же `moon.sqlite`, перезапуск читает вместо пересчёта. Regolith уже применяет этот приём. |
| Мешинг (Transvoxel, LOD0..N) | Отдельный поток(и), `threaded_update_enabled=true` | Умеренно | Нет — SQLite не хранит меши, только voxel-блоки; меш всегда строится заново из SDF при загрузке блока в LOD-терейн, кэш здесь не участвует. |
| Построение формы коллайдера (`create_trimesh_shape`/`ConcavePolygonShape3D` из vertex-массива меша) | **Главный поток**, обязательно (`PhysicsServer3D` не thread-safe — issue [#124](https://github.com/Zylann/godot_voxel/issues/124)) | **3–20×** дороже меша ([Performance](https://voxel-tools.readthedocs.io/en/latest/performance/#shape-creation-is-very-slow), issue [#54](https://github.com/Zylann/godot_voxel/issues/54): «20 times slower than creating the visual mesh», debug 80ms/release 8ms **на один блок 32³**) | **Нет.** Плагин не сохраняет и не загружает форму коллайдера откуда-либо — она не персистентна в принципе, ни в SQLite, ни где-либо ещё. Каждый раз, когда блок появляется в памяти (join, перезаход в зону, отмена LOD), форма строится заново из текущих вершин меша. |
| Регистрация тела/формы в `PhysicsServer3D` (add_shape, body transform, layer/mask) | **Главный поток**, обязательно | Часть той же главной-поточной стоимости, не отделена профилировщиком отдельно | **Нет** — это вызов движка Godot конкретного процесса; ни host, ни guest не могут «получить» чужую зарегистрированную PhysicsServer-форму по сети или из файла, у каждого свой процесс, своя `PhysicsServer3D`, свой RID. |

Итог: единственная стадия, которую персистентный SQLite-кэш действительно
устраняет — генерация SDF при перезапуске (уже сделано,
`save_generator_output = true`). Стадия, которую док называет виновником
просадки (построение формы + регистрация — главный поток, 3–20×), в принципе
не кэшируема через API плагина.

## 2. Поддерживает ли VT персистентность коллайдеров?

Проверено: официальная схема БД и код стрима.

- [`Streams`](https://voxel-tools.readthedocs.io/en/latest/streams/) —
  `VoxelStream` (включая `VoxelStreamSQLite`) описан явно как «save and load
  **voxel data** … They don't hold voxel data in memory, they are just an
  access point to different file formats» — контракт с самого начала
  ограничен voxel-данными, не производными геометрии.
- [`SQLite format v1`](https://voxel-tools.readthedocs.io/en/latest/specs/sqlite_format_v1/) —
  полная схема: таблица `meta` (version, block_size_po2, coordinate_format),
  таблица `blocks` (`loc` PK, `vb` BLOB — voxel data по Block-формату,
  `instances` BLOB — instance-данные), таблица `channels` (формат каналов,
  сейчас не используется движком). **Нет ни одной колонки под mesh или
  collision shape** — схема физически не может нести коллайдер.
- [`VoxelLodTerrain` API](https://voxel-tools.readthedocs.io/en/latest/api/VoxelLodTerrain/) —
  нет метода вида `set_collision_shape(pos, lod, shape)` или
  `load_precomputed_collider`; коллайдер получают исключительно через
  внутренний путь mesh→`create_trimesh_shape`, вызываемый движком, не
  скриптом.
- Issue [#124](https://github.com/Zylann/godot_voxel/issues/124) (автор
  Zylann, «Create collision shapes from the meshing thread», открыт с 2020,
  до сих пор не закрыт): пытался перенести построение формы в поток
  мешинга — не вышло, ровно потому что `PhysicsServer3D` не thread-safe;
  автор пометил задачу заблокированной до апстрим-фикса Godot
  (proposal [#483](https://github.com/godotengine/godot-proposals/issues/483),
  не решён). Если бы кэш/предзагрузка формы были возможны через API, этот
  issue был бы неактуален — сам факт, что автор всё ещё ищет способ
  избежать главного потока **изнутри одного процесса**, подтверждает, что
  «принести готовую форму снаружи» тоже не вариант: результат
  `create_trimesh_shape` — это Godot `Shape3D` resource с внутренним
  native-состоянием (`RID` в `PhysicsServer3D`), не сериализуемый
  байт-массив, который можно записать в SQLite и раздать другому процессу.
- Issue [#54](https://github.com/Zylann/godot_voxel/issues/54) (2019) —
  тот же вывод с числами: «Creating a collision mesh is 20 times slower
  than creating the visual mesh… Also Godot builds a BVH when TriangleMesh
  is created, which is completely useless when Bullet is used». Обсуждали
  обход через `set_faces()` напрямую (пропустить лишний BVH) — это
  микрооптимизация **внутри** построения формы на месте, не кэш извне.

Вывод: VT персистит **только SDF/voxel-данные** (что Regolith уже
использует через `VoxelStreamSQLite` + `save_generator_output`). Коллайдер —
runtime-only производная меша, API для его хранения/подмены не существует.
Чтобы реализовать идею пользователя, пришлось бы не использовать VT-API, а
патчить движок плагина (как в Regolith уже делается для visual RT-геометрии
через `Y:\godot_voxel` патч) — но и там пришлось бы решать нерешённую
апстримом проблему потокобезопасности `PhysicsServer3D`, а не просто «читать
байты из SQLite».

## 3. Масштаб: тянет ли предпосчёт всего мира на LOD0?

Планетоид: `MoonGeometry.DIAMETER_M = 19000`, `SURFACE_RADIUS_M = 9500`,
`VOXEL_SCALE = 1.0`, `DEFAULT_MESH_BLOCK_SIZE = 16`, `DEFAULT_LOD_COUNT = 10`.

- Площадь поверхности сферы: `4·π·r² = 4·π·9500² ≈ 1.1345×10⁹ м²`.
- LOD0 mesh-блок — куб 16×16×16 м, «наземный след» ≈ 256 м². «Полный
  коллайдер LOD0» физически означает покрытие всей коры хотя бы одним
  слоем блоков вдоль поверхности (реальный крust толще — под и над
  условной нулевой отметкой), т.е. **нижняя граница**:
  `1.1345×10⁹ / 256 ≈ 4.43×10⁶ блоков` только для одного слоя; с разумным
  запасом по толщине коры (2–3 слоя блоков для рельефа/пещер) —
  **9–13 млн блоков**.
- Для сравнения — реальный измеренный объём **одной сессии активной игры**
  (не всего мира, только область, куда фактически заходил игрок):
  `docs/_verify/VOXEL-TOOLS-COOP-DIG.md` не даёт, но `bootstrap.gd:594`
  прямо документирует: **«~21784 blocks / 108 MB per session»** — т.е.
  ~4.96 КБ/блок сжатых voxel-данных (без коллайдера/меша). Полный мир
  LOD0 — это **~200–600× больше блоков**, чем всё, что игрок реально
  посещает за игровую сессию.
- Только SDF-хранилище (по той же цене за блок, **без** учёта коллайдера):
  `9×10⁶ блоков × ~5 КБ ≈ 43–65 ГБ`. Плюс форма коллайдера
  (`ConcavePolygonShape3D` faces array) обычно **тяжелее** сжатого SDF
  блока — сырые треугольники несжаты по природе; консервативно
  ×2–5 от SDF-объёма → ещё **+90–300 ГБ**, если бы такое хранение вообще
  было возможно (см. §2 — невозможно через API).
- Время: issue #54 — единичный блок 32³ (в 8 раз объёмнее блока 16³)
  стоит ~8 мс (release) на построение формы коллайдера **на главном
  потоке**. Блок 16³ дешевле, но не линейно (BVH/накладные расходы) —
  консервативно ~2–4 мс/блок. `9×10⁶ блоков × ~3 мс ≈ 7.5 часов`
  **непрерывной работы главного потока** только на коллайдеры, не считая
  генерации SDF (уже отмечено как «heavy» для аналитического генератора
  Ø19 км) и мешинга. Это неприемлемо как этап загрузки игры при любой
  вменяемой длительности лоадскрина.

Вывод: «весь L0-коллайдер сразу на старте» нежизнеспособен по объёму и
времени независимо от вопроса про SQLite — это на 2–3 порядка больше, чем
когда-либо нужно одновременно любому количеству одновременных viewer'ов
(host view_distance 512 воксель, гость 48 воксель — оба на 2–3 порядка
меньше полного шара).

## 4. Помогает ли это конкретно co-op / host FPS?

**Нет.** Причина — независимая от SQLite архитектура Godot:

- Host и guest — это **два отдельных процесса** Godot, каждый со своим
  `PhysicsServer3D`, своим RID-пространством. Нельзя «переслать» готовую
  зарегистрированную форму коллайдера от одного процесса другому ни по
  сети, ни через общий файл — регистрация в `PhysicsServer3D` **обязана**
  выполняться локально, в главном потоке того процесса, которому нужно
  физическое тело.
- Даже если бы VT поддерживал сериализацию формы коллайдера в байты (не
  поддерживает, см. §2), десериализация всё равно требует вызова
  `PhysicsServer3D.shape_create`/`body_add_shape`-эквивалента — **на главном
  потоке**, с той же ценой регистрации, которую доклад называет проблемой.
  SQLite убирает самое дешёвое (чтение диска), не убирает самое дорогое
  (create_trimesh_shape + PhysicsServer registration).
- Текущий bulk-join уже частично делает «получить из SQLite»: 
  `apply_coop_terrain_bulk` (`bootstrap.gd:187`) шлёт гостю байты
  `moon.sqlite` целиком при джойне. Но это voxel-данные для *генерации*
  меша/коллайдера гостем локально по мере стриминга — не готовый
  коллайдер. Это уже правильный паттерн (избегает пересчёта SDF-коры на
  госте), просто он не имеет отношения к стоимости построения коллайдера
  на **host**-стороне, которая и есть заявленная проблема (2–5 FPS при
  «дигг + движение» именно на host).
- Итого: предложение адресует не ту стадию. Проблема — 3–20× cost
  построения формы + main-thread регистрация; SQLite-кэш решает только
  I/O чтения SDF, который и так не в top-3 подозреваемых по офиц. доке.

## 5. Что в идее верно / уже есть

- **«Перестраивать только изменённую часть коллайдера при правке»** — это
  ровно то, как VT работает нативно: блочная архитектура означает, что
  правка (`do_sphere`/`do_box`) помечает dirty только пересекающиеся
  LOD0-блоки; мешинг и коллайдер перестраиваются точечно для них, не для
  всего терейна. `bootstrap.gd:428` (`lod.collision_update_delay =
  TERRAIN_COLLISION_UPDATE_DELAY_MS`) — это именно официальный механизм
  коалессировать *несколько* правок в *одну* пересборку формы на
  задетый блок, что покрывает и «throttling»-часть идеи. Добавлять здесь
  нечего — уже сделано.
- **«Персистировать, чтобы не пересчитывать заново»** — верно для SDF/
  генератора (уже реализовано: `save_generator_output = true`,
  комментарий в `_configure_dig_stream` явно называет причину — «Ø19 km
  analytic gen is heavy»). Идея пользователя интуитивно правильно нацелена
  на «не пересчитывать дорогое», просто ошиблась стадией — коллайдер,
  а не SDF, и коллайдер как раз то, что API не даёт кэшировать.
- **Общий SQLite для host/guest** — тоже частично уже есть (bulk join
  sync шлёт `moon.sqlite` целиком), просто это не про коллайдер, а про то,
  что уже упомянуто в §4.

## 6. Альтернативы (ранжировано)

| # | Альтернатива | Impact на репортед FPS | Effort | Risk | Что решает / не решает |
|---|---|---|---|---|---|
| 1 | Измерить `get_statistics()`/`remaining_main_thread_blocks` живьём во время «дигг+движение» (уже рекомендовано в `VOXEL-TOOLS-COOP-DIG.md` §7.2) | — (это диагностика, не фикс) |低 (минуты) | Нет | Подтверждает/опровергает саму гипотезу «bottleneck = коллайдеры главного потока» **до** траты усилий на что-либо ниже |
| 2 | Занизить `secondary_lod_distance` для гостевого/ровер-viewer отдельно от `lod_distance` | Средний-высокий, если LOD>0 вокруг гостя тянет лишние данные/переходные коллайдеры | Низкий (1 строка) | Низкий | Уменьшает объём данных/переходных мешей вокруг viewer, не трогает частоту edit'ов |
| 3 | `voxel/threads/main/time_budget_ms` A/B (поднять с ~8мс) | Средний — размазывает пик по кадрам вместо просадки, ценой средней устойчивости | Низкий (project setting) | Средний (риск подвисаний на пиках) | Не уменьшает суммарную работу, только перераспределяет; может ухудшить P99 |
| 4 | Рейт-лимит на гостевые dig-команды отдельно от локальных (issue #225/#72 совет) | Средний, если гость спамит edits быстрее, чем locally throttled | Средний (найти путь в `terrain_excavation_service`/coop replay) | Низкий | Уменьшает **количество** пересборок формы в единицу времени — прямое попадание в §1 «стадия 3» |
| 5 | Держать `HostStreamViewer` персистентным (view_distance→0 вместо create/destroy) вместо `queue_free`/`add_child` на каждый toggle инструмента — если API позволяет `view_distance=0` = «не стримить» (не проверено) | Неизвестно, требует профилирования toggle-момента | Средний | Средний (не подтверждено, что Clipbox дёшево реагирует на `view_distance=0`) | Может убрать всплеск пересчёта Clipbox-состояния именно в момент начала копания гостем |
| 6 | `collision_lod_count` — ограничить, на скольких LOD генерируются коллайдеры (сейчас `SPAWN_COLLISION_LOD_COUNT=3`, уже ограничено не-0/all) | Низкий доп. impact, уже частично применено | — | — | Уже сделано в проекте, упомянуть как «не трогать без числа» (комментарий `bootstrap.gd:1333`) |
| 7 | Полностью отключить `requires_collisions` на госте, если `is_area_editable` можно проверять только по voxel-данным без физической формы (сверить с VT API — не проверено в этом research) | Потенциально высокий, если применимо | Средний (нужна проверка семантики `is_area_editable`) | Средний | Возможно устраняет саму причину доп. коллайдеров под гостем, а не просто их дозирует |
| 8 | **Предложение пользователя (SQLite-кэш полного L0-коллайдера)** | Нулевой — не адресует main-thread build/register стадию (см. §4), плюс нежизнеспособно по объёму/времени (см. §3) | Очень высокий (нужен патч VT C++, обход нерешённого upstream issue #124/#483) | Высокий | Не рекомендуется |

Для двух репортед кейсов:

- **«2–5 FPS во время дигг+движение»** — из ranked-списка ближе всего #1
  (диагностика), затем #4 (rate-limit гостевых edits) и #2
  (`secondary_lod_distance`) — это прямые рычаги против стадии
  построения/регистрации формы, которую называет офиц. дока.
- **«~30 FPS пассажир на сиденье»** — уже частично закрыт кодом
  (`_host_needs_terrain_stream` отключает viewer при seat_id > 0,
  комментарий явно ссылается на этот регресс); #5 (не разрушать/пересоздавать
  viewer) может добавить ещё, если код когда-то включит collision-viewer и
  для пассажиров.

## 7. План измерения (перед тем как строить что-либо)

1. Хук на `VoxelLodTerrain.get_statistics()` (или `VoxelEngine.get_stats()`)
   каждые N кадров в debug-оверлей/консоль во время playtest «гость
   копает + host на ровере»:
   - `remaining_main_thread_blocks` — если стабильно > 0 и не падает во
     время просадки → подтверждает bottleneck на главном потоке
     (мешинг+коллайдер), не в GDScript-логике coop.
   - `blocked_lods` / `dropped_blocks` (сверить точные имена полей в
     текущей версии API — `VoxelLodTerrain` doc, раздел `get_statistics`) —
     индикатор, что главный поток не успевает за темпом правок.
2. `debug_draw_viewer_clipboxes = true` на живом host — сравнить
   реальный размер гостевого clipbox с ожидаемым (48 воксель LOD0);
   раздутие само по себе — отдельная находка.
3. Профилировать (Godot profiler / `Time.get_ticks_usec()` bracket) именно
   момент `_ensure_host_stream_viewer()`/`_release_host_stream_viewer()` —
   единичный всплеск в кадре toggle-а инструмента отдельно от устойчивой
   просадки во время самого копания.
4. Если `remaining_main_thread_blocks` **не** растёт во время просадки —
   гипотеза «bottleneck = VT-коллайдеры» отклоняется, и проблему нужно
   искать в `coop_session.gd` (RPC/сериализация dig_ops) или в Jolt/
   RigidBody-стороне ровера — не в VT.
