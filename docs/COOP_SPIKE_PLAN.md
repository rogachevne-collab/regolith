# COOP-SPIKE: «вместе бегать, копать, строить и кататься»

Цель спайка — играбельный кооп-вечер на двух машинах через Tailscale:
бегаем/прыгаем, видим друг у друга бур, строим, копаем, один водит ровер —
второй едет пассажиром.

**Статус (2026-07-25, код написан, приёмка глазами НЕ пройдена, не закоммичено):**
- Этап A — сделан: `"tool"` в позе, `ToolHolder` под головой аватара, код-билт бур.
- Этап B — сделан для `voxel_remove`/`scoop_spoil`/`dump_scoop`: op-ребродкаст
  `_cli_dig_op` (CH_MAIN), `WorldCommandGateway.replay_remote_dig`, штамповка
  подтверждённых объёмов. Остался только `dig_terrain_debris` — см. ниже,
  это НЕ «просто разблокировать», обломки требуют своей мини-репликации.
- Этап C — сделан целиком (код): стрим движущихся сборок `_cli_assembly_motion`
  (15 Гц, CH_STREAM) + посадка гостя через per-peer occupancy (без угона
  `_rover_seat_*` хоста) + реле руля `_srv_control_input` на CH_STREAM
  (20 Гц, НЕ команда гейтвея) + поле `"seat"` в позе для аватара на кресле.
  Приёмка глазами в двух окнах — ещё нет.
- Этап D — сделан (код): `passenger_seat` slice01-деталь (ControlSeat без
  руля), посадка через `toggle_control_seat` + `passenger: true` / archetype,
  freelook, `"seat": element_id` в позе; водитель vs пассажир разведены
  (`is_local_seat_driver`, без `_srv_control_input` / locomotion для PAX).
  Приёмка глазами — нет.

Это НЕ спецификация с нуля. Формальная спека этапов лежит в
`docs/specs/COOP-HOST-V0.md` — прочитать её ПЕРЕД началом любого этапа.
Этапы 0–3 уже реализованы и работают. Этот документ — порядок работ спайка
поверх неё + конкретные точки входа в код.

## Карта кода (прочитать перед любым этапом)

| Файл | Что это |
|---|---|
| `scripts/coop/coop_session.gd` | ВЕСЬ сетевой транспорт. Один узел `CoopSession` в `main.tscn`, одинаковый NodePath у всех пиров — иначе @rpc не резолвится. Ничто другое в игре не трогает `multiplayer`. |
| `scripts/coop/coop_command_codec.gd` | Чистая сериализация: `sanitize_command` (вырезает живые Object, `target.collider`, `placement_plan`), `BLOCKED_KINDS`, handshake/join payload. Покрыт `scripts/test_coop_codec.gd`. |
| `scripts/coop/remote_player.gd` | Аватар чужого игрока. Без физтела. Визуал строится В КОДЕ (`_build_visuals`), сцена `scenes/remote_player.tscn` — голый Node3D. Интерполяция 120 мс по кольцу семплов. |
| `scripts/coop/coop_peer_registry.gd` | host-only реестр peer_id → uid/nick/avatar. |
| `scripts/world_command_gateway.gd` | Все игровые действия — команды через него. `set_network_submit(hook)` — клиентский перехват, `submit_as(uid, cmd, avatar)` — хост исполняет от имени пира, `complete_remote(local_id, result)` — вернуть результат клиенту. |
| `scripts/tool_controller.gd` | Активный инструмент/хотбар локального игрока. |
| `scripts/drill.gd` | Бур (first-person визуал — источник меша для third-person префаба). |

Ключевые константы транспорта (`coop_session.gd`):
- Каналы: `CH_MAIN=0` (reliable: команды/результаты/peer up-down),
  `CH_BULK=1` (reliable: join payload + снапшоты), `CH_STREAM=2`
  (unreliable_ordered: позы 20 Гц + suit-sync 1 Гц).
- `POSE_INTERVAL=0.05` → позы УЖЕ летят 20 Гц, и в позе УЖЕ есть кватернион
  головы `qh` (см. `_local_pose()`: `{p, q, qh, l, v}`). Направление взгляда
  синхронизировано с этапа 3 — для этапа A НЕ надо трогать частоты и не надо
  добавлять yaw/pitch, они уже в `qh`.
- Снапшот-ребродкаст: `_mark_snapshot_dirty()` → debounce 0.3 c, пол 1 c,
  `_cli_apply_snapshot` → `world.restore_snapshot`. Кинды из
  `NO_BROADCAST_KINDS` (копка/грануляр) снапшот НЕ триггерят — осознанно,
  чтобы бур хоста не штормил клиентов ребилдами.
- Поток команды клиента: `_on_local_submit` (клиент, блок-лист здесь) →
  `_srv_submit` (хост) → `_gateway.submit_as(...)` → `_on_host_command_completed`
  → `_cli_result` → `_gateway.complete_remote`. Клиент свою команду локально
  НЕ исполняет — только хост, клиенту прилетает результат + снапшот.

Порядок этапов — от дешёвой радости к тяжёлой физике; каждый этап приёмный
сам по себе, спайк можно остановить после любого. A и B независимы от C/D.

## Этап A. Живой аватар: бур в руках, следящий за взглядом

**Что хотим видеть:** у чужого аватара в руках third-person бур, ствол ходит
за взглядом (голова уже синхронизирована), при смене слота хотбара меняется
и предмет в руках.

### Что именно сделать

1. **Расширить словарь позы** в `CoopSession._local_pose()` одним полем:
   `"tool": <StringName/int id активного инструмента>`. Источник — спросить
   `tool_controller.gd` (найти там текущий выбранный инструмент/слот; если
   публичного геттера нет — добавить, не лезть в приваты снаружи).
   Поза — плоский Dictionary, идёт МИМО кодека (это ок, там нет Object'ов);
   `sanitize_command` трогать не надо.
2. **`RemotePlayer.push_pose`**: добавить `"tool"` в семпл (по образцу `"l"`),
   в `_apply(...)` пробросить и вызвать `_set_tool(tool_id)`.
3. **`RemotePlayer._build_visuals`**: добавить `_tool_holder := Node3D.new()`
   ребёнком `_head` (НЕ корня!). `_head` уже получает полный базис головы в
   `_apply` (`_head.global_basis = Basis(head_q)`) — всё, что висит под ним,
   бесплатно следит за взглядом, как уже делает `Headlamp`. Ставить холдер
   чуть вбок/вниз от головы (примерно `position = Vector3(0.25, -0.25, -0.4)`,
   подобрать глазами), ствол вдоль локального -Z (как SpotLight — «вперёд»
   у головы это -Z).
4. **Third-person меш бура**: открыть `scripts/drill.gd` и сцену бура, найти
   MeshInstance3D. Собрать ЛЁГКИЙ префаб `scenes/remote_tool_drill.tscn`:
   только меши, без скриптов, без звука, без коллайдеров, без частиц.
   НЕ инстансить first-person сцену целиком — она предполагает камеру-родителя.
5. `_set_tool(id)`: держать словарь `id → PackedScene` в `remote_player.gd`
   (для спайка достаточно бура и «пусто»; остальные слоты → пусто). Кэшировать
   текущий id, пересоздавать ребёнка холдера только при смене.

### Грабли

- НЕ добавлять новых @rpc-методов ради этого — поле едет в существующем
  `_srv_pose`/`_cli_pose`. Если всё же добавляешь @rpc: метод обязан
  существовать в `coop_session.gd` у ОБЕИХ сторон (один класс — ок) и
  сигнатуры/каналы должны совпадать.
- Прыжки уже гладкие: в позе есть `v`, `_apply_extrapolated` экстраполирует.
  Не трогать.
- Ничего не менять в `PROTOCOL_VERSION`: новое поле позы читается через
  `pose.get("tool", ...)` с дефолтом — старых клиентов в природе нет,
  но дефолт обязателен, поза может прийти и без поля.

### Приёмка (глазами, два окна на одной машине достаточно)

Два окна: первое `host`, второе `join 127.0.0.1` (uid разрулится сам через
loopback-мьютекс). Во втором окне взять бур, водить мышью вверх-вниз,
попрыгать, переключить слоты. В первом окне: бур виден, ходит за взглядом,
исчезает при смене слота. Никаких тестов на визуал.

## Этап B. Копка в коопе (минимальный «этап 4»)

Сейчас копка запрещена в двух местах: `CoopCommandCodec.BLOCKED_KINDS`
(клиент режет у себя с `not_in_coop_yet`) и — отдельно — дырка в снапшотах:
`NO_BROADCAST_KINDS` в `coop_session.gd` не даёт копке хоста триггерить
снапшот, поэтому ямы хоста клиент не видит вообще.

**Принцип — реплицируем ОПЕРАЦИИ копки, не поле и не снапшоты террейна.**
Оба пира идентичный double-билд с одинаковым `seed`/`generator_version`
(это уже проверяет handshake) — применение одной и той же dig-операции к
одинаковому полю даёт одинаковый результат с точностью до дрейфа, который
для спайка принимаем.

### Что именно сделать

1. **Разобраться, кто исполняет dig-кинды.** Найти обработчики
   `voxel_remove`, `dig_terrain_debris`, `scoop_spoil`, `dump_scoop` — идти от
   `world_command_gateway.gd` вниз в `scripts/simulation/runtime/*`. Выписать:
   какие поля команды реально нужны исполнителю и что из них вырезает
   `sanitize_command` (он удаляет `target.collider`!). Это главный вопрос
   этапа: комментарий в кодеке прямо говорит `dig_terrain_debris — needs live
   target.collider`. Решение для спайка: научить хостовый исполнитель
   резолвить цель по позиции/нормали из `target` (позиция в команде остаётся),
   а не по живому коллайдеру. Если это дорого — оставить в блок-листе только
   этот кинд, остальные выпустить.
2. **Убрать выпущенные кинды из `BLOCKED_KINDS`** (кодек) — клиентская копка
   поедет на хост существующим путём `_srv_submit`.
3. **Новый ребродкаст подтверждённой операции.** В
   `_on_host_command_completed` (хост): если `status == ok` и кинд — dig,
   то вместо `_mark_snapshot_dirty()` собрать компактный op-дикт
   (кинд + позиция + параметры из исходной команды, БЕЗ Object'ов — прогнать
   через `CoopCommandCodec.sanitize_command`) и `rpc("_cli_dig_op", op)` на
   `CH_MAIN` (reliable! потерянная яма = вечный дрейф). Новый @rpc-метод
   `_cli_dig_op` в `coop_session.gd`: применить op к ЛОКАЛЬНОМУ полю клиента
   напрямую через тот же исполнитель, МИМО gateway (мимо списаний ресурсов —
   см. п.5). ВАЖНО: хост шлёт `rpc(...)` — это все пиры; автор команды тоже
   получает op и применяет так же (клиент свою копку локально не исполнял,
   эха не будет).
4. **`NO_BROADCAST_KINDS` не трогать** — снапшоты по-прежнему не должны
   дёргаться от копки. Дырка закрывается новым op-каналом, не снапшотами.
5. **Ресурсы.** Начисление выкопанного происходит только на хосте внутри
   нормального исполнения команды (per-peer store уже есть, `submit_as`
   стамает uid пира). Клиентский локальный «проигрыш» op-а НЕ должен второй
   раз трогать сторы — применять только терраформ/грануляр-часть. Если
   исполнитель не разделяется на «поле» и «ресурсы» — разделить (два метода).
6. **Джойнер после ям.** Новый клиент получает join payload со снапшотом, но
   снапшот террейн не несёт (см. `NO_BROADCAST_KINDS` и спеку). Для спайка:
   записать в известный долг «джойнер не видит старые ямы» — копаем после
   того, как все собрались. В доке долга (внизу) уже есть.

### Отдельная история: летающие обломки (`dig_terrain_debris`)

Разведка 2026-07-24 показала: обломки породы — НЕ симуляционные элементы.
`TerrainFloatingDebrisService` спавнит их как сценные RigidBody3D в группе
`terrain_floating_debris`, всё состояние (hp) — в метах тела
(`dig_hp`/`dig_hp_max`/`dig_mass_kg`), в снапшоты они не попадают.
Следствия:
- Клиент обломков НЕ ВИДИТ вообще (реплей копки намеренно гейтит
  `_maybe_separate_floating_chunks`, чтобы не плодить локальные копии,
  которые некому потом удалять).
- «Разблокировать кинд» недостаточно: `_dig_terrain_debris` работает с живым
  `body` (меты, scale, impulse, queue_free) — по сети это не переносится.

Правильная форма (средний кусок, НЕ мелочь): мини-репликация обломков.
1. При спавне на хосте — сетевой id в мету тела; спавн-оп клиентам
   (id, размер/меш-сид, transform) по CH_MAIN.
2. Моушен обломков — подкладывать в существующий стрим сборок или отдельным
   батчем по CH_STREAM (это просто rigid-тела, у клиента — frozen kinematic).
3. `dig_terrain_debris`: клиент кладёт в команду сетевой id (коллайдер и так
   вырезается), хост резолвит тело по id; hp/scale-апдейт и despawn — опом
   по CH_MAIN (`destroyed` уже есть в результате обработчика).
Пока это не сделано — кинд остаётся в блок-листе, и это осознанно.

### Грабли

- Один headless Godot за раз при проверках; бинарь —
  `Y:\godot-engine\bin\godot.windows.editor.double.x86_64.console.exe`.
- Два окна на одной машине пишут в один dig SQLite — для локального теста
  копки второе окно запускать с `-- --coop-sandbox=guest` (изолирует user://).
- Не изобретать свой формат op-а: op = санитайзнутая команда + кинд, тот же
  словарь, что уже ходит в `_srv_submit`.
- `test_coop_codec.gd` расширить ТОЛЬКО на изменения кодека (какие кинды
  разблокированы). Логику поля тестами не покрывать — приёмка глазами.

### Приёмка

Две машины (или два окна с sandbox-флагом): оба копают одну яму по очереди
в одном месте. Яма «одинаковая на глаз» у обоих; ресурс начислился копавшему
и не задвоился (смотреть HUD-инвентарь обоих).

## Этап C. Ровер: гость водит, все видят движение

Сейчас: физика сборок тикает только на хосте (`world.authoritative = false`
у клиента после `_apply_join`), клиент видит сборки замороженными между
снапшотами. Сесть в кресло клиент не может: `toggle_control_seat` в
`BLOCKED_KINDS` («needs collider + reparent»).

**Принцип: физика ТОЛЬКО на хосте.** Гость шлёт ввод, хост симулирует,
хост стримит трансформы движущихся сборок. Никакой клиентской физики машин.

### Что именно сделать

1. **Прочитать спеки** `docs/specs/ROVER-MODULES-V1.md` и
   `docs/specs/CONTROL-ACTIONS-V0.md` — как устроены кресло, управление и
   команды управления. Ключевые файлы дальше:
   `scripts/simulation/projection/simulation_physics_projection.gd` (тела ↔
   сим), `scripts/simulation/runtime/wheel_simulation_service.gd` (колёса),
   `scripts/simulation/projection/element_visual_projection.gd` (визуалы),
   `scripts/ui/hud_control_terminal.gd` (место, где `toggle_control_seat`
   уходит в gateway).
2. **Посадка гостя.** Находка разведки 2026-07-24: коллайдер — НЕ главная
   проблема (`_toggle_control_seat` и так резолвит по
   `InteractionHit.element_id_from(target)`, id в санитайзнутой команде
   выживает). Настоящий блокер — `command["source"]`: у гостевой команды на
   хосте это его RemotePlayer-аватар, а `_enter_rover_seat` завязан на
   ОДНОМЕСТНУЮ сит-машину гейтвея (`_rover_seat_player` /
   `_rover_seat_assembly_id` / `_rover_seat_policy`) — посадка гостя через
   неё угонит кресло-стейт самого хоста. Правильная форма:
   - хост для НЕ-локального актёра (actor_uid != uid хоста) не трогает
     `_rover_seat_*`, а только клеймит occupancy в мире —
     `SimulationWorld._player_seat_contexts` (player_id → seat element_id,
     эфемерно, не снапшотится) уже существует, нужен публичный
     claim/release API с отказом `occupied`;
   - клиент на `ok` локально присасывает СВОЕГО игрока к СВОЕЙ реплике
     кресла (element id тот же после restore_snapshot) — камера/тело
     локальны, физики не надо: кресло едет стримом сборок, игрок с ним;
   - выход — release тем же киндом; на дисконнекте пира хост чистит его
     occupancy (в `_on_peer_disconnected`).
3. **Ввод руля — отдельный stream-RPC, НЕ команда гейтвея.** Локальный
   ввод хоста и так идёт мимо очереди команд
   (`SimulationSession._physics_process` → `gateway.tick_rover_locomotion_input()`).
   Оборачивать руль в кинд `control_input` нельзя: `_on_host_command_completed`
   помечает мир dirty для любого `ok` вне `NO_BROADCAST_KINDS` — команда на
   20 Гц устроила бы snapshot-ребродкаст + reliable-эхо результата на каждый
   кадр ввода. Вместо этого: клиент сэмплирует raw через
   `gateway.collect_seat_raw_input()` (edge-флаги копятся каждый физтик),
   шлёт `rpc_id(1, "_srv_control_input", raw, edges)` на `CH_STREAM`
   (unreliable_ordered) каждые 50 мс пока сидит; хост зовёт
   `gateway.apply_remote_driver_input(uid, raw, edges)` → `SeatInputRouter` +
   `apply_driver_frame`. Пакеты слать постоянно (не «только при изменении»):
   потерянный нулевой кадр по unreliable иначе оставит газ. Watchdog >300 мс
   без пакета — `clear_driver_input`.
4. **Стрим трансформов сборок.** Новое в `coop_session.gd` по образцу поз:
   - хост в `_physics_process` раз в `ASSEMBLY_INTERVAL := 1.0/15.0` собирает
     список ДВИЖУЩИХСЯ сборок (порог по linear/angular velocity корневого
     тела; спящие не стримим — иначе зря греем канал) из
     physics-проекции;
   - пакет: `{assembly_id: {"t": Transform3D корня, "w": [углы колёс]}}`,
     `rpc("_cli_assembly_stream", batch)` на `CH_STREAM` (unreliable_ordered,
     как позы);
   - клиент: применить трансформ к своей реплике сборки. Выяснить в
     physics-проекции, как у клиента живут тела реплики: если физтела есть —
     на время стрима перевести в freeze/kinematic и двигать трансформом; если
     клиентская проекция и так не симулирует (authoritative=false) — просто
     ставить трансформ узла. Интерполяцию взять готовую из `remote_player.gd`
     (буфер семплов + render_t − 120 мс) — вынести в маленький общий хелпер
     или скопировать, не изобретать новую.
   - когда сборка остановилась, стрим по ней прекращается; очередной обычный
     снапшот (постройка и т.п.) её всё равно поправит.
5. **Латенцию руля гостя принять.** Ввод → хост → стрим назад ≈ RTT+66 мс.
   Для спайка ок. Никакого client-side prediction.

### Грабли

- Снапшот (`_cli_apply_snapshot` → `restore_snapshot`) может прилететь ВО
  ВРЕМЯ езды (кто-то построил блок) и пересоздать/сбросить сборки. После
  применения снапшота клиент должен заново применить последний семпл стрима
  к движущимся сборкам (сохранить последний батч и переприменить).
- Не слать стрим пирами, которым он не нужен, — в спайке шлём всем, это ок
  при 8 пирах максимум (`MAX_PEERS`).
- Кресло — авторская деталь: помнить про [две парадигмы деталей] — если
  тестовый стенд только с сеточными блоками, зелёный тест ничего не докажет.
- Wheel-perf: HUD/vpwr завязаны на снапшоты индустрии — не будить панели
  каждый тик стрима, стрим — чисто трансформы.

### Приёмка

Две машины. Гость подходит к роверу хоста, садится, едет. У хоста ровер
едет плавно (не слайдшоу и не телепорты), у гостя руль отзывается с
терпимой задержкой. Потом наоборот: хост водит — гость смотрит со стороны.

## Этап D. Пассажирское кресло (mini-cockpit)

Стоять на едущем ровере физикой — заведомо флаки (кинематик-платформа +
сетевой стрим), в спайк не берём. Кресло-деталь, как и предлагалось.

### Что именно сделать

1. **Новая авторская деталь «Passenger Seat»**: по пайплайну
   `docs/authoring_parts.md`. Маунт на строительную сетку (0.5 м), без
   органов управления — только anchor-точка сидения.
   ⚠ Испечённая деталь МОЛЧА МЕРТВА, если её archetype_id нет в hardcoded
   реестрах (питание, интеракции и др.) — пройтись по местам из памяти
   [authored-parts-hardcoded-registries], проверить интеракцию «сесть».
2. **Посадка** — тот же механизм, что кресло управления из этапа C, но обработчик
   НЕ захватывает управление: игрок фиксируется к anchor, камера свободна.
   Проще всего: тот же кинд `toggle_control_seat` (или его брат) с флагом
   `passenger: true` в параметрах.
3. **Сетевое — бесплатно поверх C.** В позу игрока (`_local_pose`) при посадке
   `"seat": element_id` (0 = пешком). `RemotePlayer._apply`: если `seat > 0` —
   позиция аватара = transform кресла локальной реплики (едет стримом этапа C).
   Голова/бур этапа A продолжают работать как есть.
4. **Выход** — обычный «встать»: seat из позы пропадает, аватар снова живёт
   по `p`.

### Приёмка

Хост ведёт ровер, гость в пассажирском кресле: оба видят друг друга на
местах, пассажир крутит камерой и «водит буром» (этап A) на ходу. Потом
поменяться ролями.

## Что сознательно НЕ в спайке (записанный долг)

- Настоящие дельты сторов/машин (этап 5 спеки) — клиент между событиями
  видит замороженную индустрию.
- Джойнер не видит ямы/кучи, сделанные до его join — **закрыто для пере-заходов
  в сессии** (2026-07-25): хост копит `_dig_ops` с `host`, join payload несёт
  массив, клиент реплеит через `replay_remote_dig` после `restore_snapshot`.
  Соло-история хоста до `host` (SQLite dig-stream bulk) — всё ещё открыта:
  2. Честно (закрывает соло-историю хоста до `host`): переслать джойнеру
     изменённые блоки voxel dig-stream'а (SQLite хранит только правки) +
     сериализацию затронутых granular-чанков, чанками по CH_BULK после
     join payload; у клиента — записать в свой стрим и сбросить LOD-меши
     затронутых регионов. capture_snapshot террейн НЕ несёт намеренно —
     не менять, это отдельный канал.
- Ресинк дрейфа террейна (контрольная сумма чанка + точечная ресинхронизация).
- Предсказание ввода водителя, клиентская физика.
- Сейв per-peer позиций; стояние на движущихся платформах.

## Рабочие правила спайка (для всех агентов)

- **Сначала прочитать** `docs/specs/COOP-HOST-V0.md` и файлы из «Карты кода».
  Не выдумывать параллельных механизмов: команды — только через gateway,
  сеть — только в `coop_session.gd`, сериализация — только в кодеке.
- **Приёмка каждого этапа — глазами**, два окна локально (`host` /
  `join 127.0.0.1`; для копки второму окну `-- --coop-sandbox=guest`),
  финально — две машины через Tailscale (`join <100.x>`). Зелёные headless
  тесты ничего не доказывают про ощущение игры.
- Быстрый локальный прогон: `tools/coop_two_windows.bat` (хост слева с
  `--coop-autohost`, гость справа с `--coop-sandbox=guest --coop-autojoin`).
  Ручной путь через консоль `host` / `join 127.0.0.1` остаётся.
- Тесты не пишем, кроме расширения `test_coop_codec.gd` при изменении кодека.
- Запуск: `Y:\godot-engine\bin\godot.windows.editor.double.x86_64.console.exe`
  (проект ЗАПУСКАЕМ, он запускается). Один headless-прогон за раз, длинное —
  в фон с выводом в файл.
- Новый `class_name` → сначала `--import`, иначе headless не увидит; цикл
  class_name'ов ломает загрузку .tres с «non-existent resource».
- Рядом работает Cursor-агент, коммитящий всё дерево: перед коммитом сверять
  `git log`/`git diff`, перед Edit перечитывать файл.
- Коммит в main после каждого этапа. БЕЗ Co-Authored-By трейлеров.
- Если меняется формат рукопожатия/join payload — бампнуть
  `CoopCommandCodec.PROTOCOL_VERSION`. Новые поля ПОЗЫ — только через
  `.get(..., default)`, версию не бампать.
